# Project rules

Scope: `sandbox-nest` is a solo learning/sandbox project, built one tutorial
"chapter" at a time (see commit history: `chapter: nest create controller
service` → `chapter: Entity` → `chapter: connect db and POST GET`). These
rules exist to keep each new chapter consistent with what came before, not to
impose process overhead on a solo repo.

## 1. Workflow

- Single `main` branch; commits land directly — no PR process needed for a
  solo sandbox. If this ever becomes a shared project, switch to feature
  branches + PRs first.
- Commit messages currently follow `chapter: <what changed>` while working
  through the tutorial track. Once past the tutorial phase (or if this
  becomes a real project), prefer
  [Conventional Commits](https://www.conventionalcommits.org/)
  (`feat:`, `fix:`, `refactor:`, `docs:`, `test:`) for a more useful
  `git log`.
- Never commit `.env` (already git-ignored) or real credentials. Keep an
  `.env.example` with placeholder keys (`DB_HOST`, `DB_PORT`, `DB_USERNAME`,
  `DB_PASSWORD`, `DB_NAME`) in sync with what `AppModule` reads.
- Run `pnpm lint` and `pnpm format` before committing.

## 2. Module structure

Every domain (`users`, `product`, future ones) lives under `src/<domain>/`
and follows the Nest CLI resource shape:

```
src/<domain>/
  dto/
    create-<domain>.dto.ts
    update-<domain>.dto.ts
  <domain>.entity.ts           <- pick ONE placement, see note below
  <domain>.controller.ts
  <domain>.controller.spec.ts
  <domain>.service.ts
  <domain>.service.spec.ts
  <domain>.repository.ts       <- when the module talks to the DB
  <domain>.module.ts
```

**Known inconsistency to resolve:** `product` currently keeps its entity in
`entities/product.entity.ts`, while `users` keeps `user.entity.ts` at the
module root. Pick one placement and use it for every future domain — see the
note in [ADR-0002](adr/0002-repository-pattern.md).

## 3. Data access

- Controllers never talk to TypeORM directly. Flow is
  Controller → Service → Repository → `Repository<Entity>`, per
  [ADR-0002](adr/0002-repository-pattern.md).
- `product.service.ts` still returns the scaffold strings generated by
  `nest g resource` — bring it in line with `users` (repository-backed) when
  that chapter lands.
- Register entities via `TypeOrmModule.forFeature([...])` inside their own
  module, not in `AppModule`.

## 4. Validation

- Every DTO is a class decorated with `class-validator` and relies on the
  global `ValidationPipe` registered in `main.ts`. Don't hand-roll validation
  in controllers or services — see
  [ADR-0006](adr/0006-validation-pipe-and-dto.md).

## 5. Testing

- Every controller/service gets a co-located `*.spec.ts` using Nest's
  testing module — follow the existing `product.controller.spec.ts` /
  `product.service.spec.ts` for the shape.
- Keep `pnpm test` green before committing.

## 6. Environment & secrets

- Read config exclusively through `@nestjs/config`'s `ConfigService` (see
  `app.module.ts`), not `process.env` directly — the one existing exception
  is `process.env.PORT` in `main.ts`.
- `synchronize: true` on the TypeORM connection is dev-only — see
  [ADR-0005](adr/0005-typeorm-synchronize-dev-only.md). Never enable it in a
  deployed environment.
