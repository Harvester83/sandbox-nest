# ADR-0002: Repository pattern to isolate TypeORM from services

Date: 2026-08-22
Status: Accepted (partially applied)

## Context

Nest's own docs sample injects `Repository<Entity>` straight into a service.
That works, but it leaks TypeORM-specific query APIs into business logic and
makes services harder to unit-test without a real (or heavily mocked)
`Repository`. The `users` domain already avoids this: `UsersRepository`
wraps `Repository<User>` (via `@InjectRepository`), and `UsersService`
depends on `UsersRepository`, not TypeORM directly.

## Decision

Every module that persists data gets its own `<Domain>Repository` provider
injected with `@InjectRepository`. Services depend on that repository class;
controllers depend only on services. This mirrors `users.repository.ts` /
`users.service.ts`.

## Consequences

- One extra file per module, but swapping ORMs, adding caching, or composing
  more complex queries later only touches the repository layer.
- Services stay easy to unit-test with a mocked repository.
- **Known gap:** `product` doesn't have a repository yet — `ProductService`
  still returns the scaffold strings generated by `nest g resource`, and
  `Product`/`CreateProductDto` are empty stub classes. Bring `product` in
  line with `users` when that chapter is implemented.
- **Known inconsistency:** `product`'s entity lives in
  `entities/product.entity.ts`, while `users`'s entity is `user.entity.ts`
  at the module root. Pick one placement (repo default going forward:
  `<domain>.entity.ts` at module root, matching `users`) and apply it to
  every module, including a follow-up move for `product`.
